destroyRendererWhenBackendIdle

fun Engine.destroyRendererWhenBackendIdle(renderer: Renderer)

Destroys renderer once this engine's backend has executed everything already queued, polling the backlog first. Native destruction itself still has no timeout.

Engine.destroyRenderer is not a plain handle release: FRenderer::terminate first waits for "all pending commands" to execute (Fence::waitAndDestroy(engine.createFence()), Filament v1.72.1 Renderer.cpp). A scene disposed while its shader programs are still being linked — an activity destroyed right after a demo opened — parks the main thread on that whole backlog, an ANR on an emulator (#3799). The inner wait covers what is queued when the destroy runs, not when it was deferred: on a shared engine, the next screen's shader compilations queued in between. So the destroy waits, through whenBackendIdle's FreshFenceProbe, until the backend has recently caught up with its queue. That inner wait then only finds what the main thread queued in the last 48 ms — main-thread time, not backend work: usually a frame or two, but a shader compilation queued in that window is still waited for. This narrows the blocking case without ruling it out. When the backend is already idle — the usual case — the renderer is destroyed one poll later, once that fence has made the round trip to the backend, exactly as safeDestroyRenderer would. On a shared engine, polling less often than every 48 ms keeps the destroy pending. Once the engine is retiring, a reached fence suffices. Five seconds triggers a warning and slower polls, never permission to destroy behind a busy fence.

FRenderer::terminate then joins the frame-info job thread, parked in a GPU fence wait unless the engine was built without the GPU frame-complete metric — see createEngine.
