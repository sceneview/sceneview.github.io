EngineWarmUp

object EngineWarmUp

Does the part of opening a 3D screen that does not need the main thread, ahead of time, on a background thread: loading Filament's native libraries, initialising the GPU driver, creating the shared EGL context the engine is built on, and building the Basis Universal tables gltfio's texture loader needs (see GltfioTextureTables).

Without it that work runs inside the composition that first calls rememberEngine and rememberModelLoader, on the main thread: on a Pixel 7a, about 55 ms of the long frame a 3D screen opens with. After a warm-up, the next createEglContext (the default eglContextCreator of rememberEngine) takes the prepared context and only has to make it current, and the first io.github.sceneview.loaders.ModelLoader finds the tables built.

Opt-in. Nothing starts it unless the app asks, because it costs every launch that does it: about 60–80 ms of CPU on its own thread, Filament's libraries and the GPU driver loaded, and one EGL context held until an engine takes it — even a launch that never shows 3D, such as a background start for a push message or a WorkManager job. Start it where a 3D screen is likely to follow:

  • from code, on any thread, a little before the 3D screen — when the user heads for it, or in Application.onCreate() for an app whose first screen is 3D:

EngineWarmUp.start()

  • or at app startup without code, by adding EngineWarmUpInitializer to the androidx.startup provider in the app's manifest:

<provider
    android:name="androidx.startup.InitializationProvider"
    android:authorities="${applicationId}.androidx-startup"
    android:exported="false"
    tools:node="merge">
    <meta-data
        android:name="io.github.sceneview.EngineWarmUpInitializer"
        android:value="androidx.startup" />
</provider>

Started at app startup, it competes with the app's own startup. Measured on a 3D first screen: on a Pixel 10 Pro XL the 3D frame fell from 194 to 151 ms and time to first frame rose from 134 to 149 ms; on a Pixel 7a, 238 to 184 ms and 140 to 145 ms (within noise). When the 3D screen is not the first one, start it after the first frame is drawn instead.

A prepared context nobody takes within 5 seconds is released; the libraries and the tables stay, so a later 3D screen still saves most of the work. A rememberEngine given its own eglContextCreator never takes the prepared context, so for such an app a warm-up only builds the tables.

What stays on the main thread, because Filament ties an Engine to the thread that creates it (its job system adopts that thread, and Engine.destroy() must run there too): building the com.google.android.filament.Engine itself. Only the work above moves.

An app that creates its own gltfio ResourceLoader, rather than through a ModelLoader, should not do it while a warm-up may still be building the tables (on a Pixel 7a, the first ~150 ms after start): Basis builds them without locking, and only SceneView's own loaders wait for that build.

@JvmStatic
fun start()

Starts the warm-up on a background thread and returns at once. Does nothing while a prepared context is waiting to be taken or being prepared, so it is safe to call more than once: after a rememberEngine took the prepared context, a new call prepares one for the next engine.
