ModelSnapshot

class ModelSnapshot @MainThread constructor(val engine: Engine, context: Context, val maxCacheBytes: Int = DEFAULT_MAX_CACHE_BYTES, modelLoader: ModelLoader? = null)

Renders glTF / GLB models into Bitmaps off screen, with no view on screen — the thumbnails of a model library, a picker grid or a share sheet.

Each image frames the whole model automatically (see ModelSnapshotOptions), from a three-quarter angle by default, lit by a neutral studio rig (image-based light plus a key and a fill light), on a transparent background: draw it over any card colour, in light and dark themes alike.

val engine = rememberEngine()
val snapshot = rememberModelSnapshot(engine)
val thumbnail = rememberModelThumbnail(snapshot, "models/chair.glb", size = 96.dp)
thumbnail.bitmapOrNull()?.let { Image(it, contentDescription = "Chair") }

What fails

The framing trusts the bounding box the glTF loader reports. A request fails — null from snapshot, ModelThumbnailState.Failed in Compose, a warning under the ModelSnapshot tag, and nothing cached — when the model cannot be loaded, when its box is empty or not finite, when its positions are quantized as normalized integers (KHR_mesh_quantization, gltfpack -cc: gltfio reports their box about 32767 times too large), when the image comes out fully transparent, or when the render times out — the GPU backend executing nothing for 30 s, or a frame it executed never reaching the image. A backend that is merely slow (shader compilation on a cold or loaded emulator) only delays the image. A whole set (ground, sky dome) is framed whole, so its subject comes out tiny: thumbnail single objects.

Its rendering has run in tests on arm64 emulators only. On an x86_64 API 30 emulator with SwiftShader, the test process died once at the first render; the cause is undiagnosed.

One at a time, on the scene's engine

A snapshotter lives on an existing Engine (the one your SceneView uses, typically) and reuses one renderer, view, scene, camera and light rig for every image. Requests queue: one model is rendered at a time, in the order asked, so a grid asking for twenty thumbnails at once never stacks twenty model loads into the same frames. A request whose coroutine is cancelled (its grid cell scrolled away) leaves the queue; if it was rendering, the render stops and its model is released before the next request starts.

What it costs the main thread

The file is read and parsed off the main thread, and the image is copied out on a background thread. The rest runs on the main thread, as Filament requires, between the frames of your scene — and costs what loading the same model into a scene costs. Each step waits, suspended and never blocking, until the GPU backend has executed what the previous one queued: a backend that falls behind (compiling shaders on a cold emulator, for seconds) slows the thumbnails down, but never fills Filament's command stream — whose next call would then wait on the main thread. Measured on an arm64 emulator with 2–5 MB textured GLBs: creating the model ≈ 130–150 ms, finalising its textures up to ≈ 0.5 s in a single frame (gltfio uploads a decoded texture in one call), two small renders 5–16 ms. A grid of textured models therefore drops frames while it fills, one model at a time. Creating a snapshotter decodes its image-based light (≈ 70 ms). Unless you pass the scene's ModelLoader, the first request builds a loader of its own (≈ 0.6 s, for its material provider), in a main-thread turn of its own rather than in the frame that asked.

Cache

Finished images are kept in a memory cache of maxCacheBytes, so a cell scrolled back into view gets its image at once. Pass 0 to disable it. An image is handed out but never cached when it was captured while the model's textures were still decoding (after a 10 s timeout), or when the model's glTF could not be read a second time to check for quantized positions — a warning is logged. That second read goes to the same source the model was loaded from, so in practice it fails for http(s) URLs when the file cache is off (FileCache.enabled = false: then no remote model's thumbnail is ever cached) or could not write the download to disk, and for a file that changed or vanished in between. Bitmaps handed out are immutable and may be shared with the cache: do not Bitmap.recycle them.

The cache is keyed by the fileLocation string, the size and the options — not by the file's contents. A model replaced at the same location (a file rewritten in place, an URL serving a new version) keeps getting the old thumbnail until it leaves the cache: call clearCache after replacing a model, or give the new version a new location.

Create it on the main thread, and call destroy (or use rememberModelSnapshot, which does) before the engine is destroyed.

Parameters

engine

the engine to render with. It must outlive this snapshotter.

context

any context; only its application context is kept.

maxCacheBytes

size of the in-memory thumbnail cache, in bytes. 0 disables it.

modelLoader

the loader to load models with, on engine — typically your scene's rememberModelLoader, which saves building a second material provider. Its texture loading is then shared with your scene's models: a thumbnail asked while the scene loads waits for those textures too (or is not cached, past the timeout). destroy does not destroy it. null (the default): the first request builds a loader of the snapshotter's own, destroyed with it. A loader passed in must outlive this snapshotter: destroy the snapshotter first. Its clear() (or a destroy()) while a thumbnail renders destroys that thumbnail's model too: the render notices before its next call on the model and the request fails (null, ModelThumbnailState.Failed in Compose) instead of crashing; later requests load again. A request made once the loader is destroyed fails the same way, but destroying it while a request is still reading its file is not covered: the load itself then calls into freed objects.
